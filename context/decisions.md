# Decisions

<!-- One line per decision: date, decision, why. -->
- 2026-11-11: Change graph uses only the standard library: Python through `ast`, the other languages through declaration patterns plus brace matching (`orch/symbols.py`). Why: nothing new to install or audit and it runs offline wherever the orchestrator runs; a real parser per language (tree-sitter) would be a native dependency. (change graph)
- 2026-11-11: The change graph is a view, never a gate: built right after the guardrails check (pass or fail), and any error is logged while the card carries on. Why: guardrails stay in code and the approval and merge path stays exactly as it was. (change graph)
- 2026-11-11: Graph snapshots are run artifacts (`runs/<run>/<card>/graph<n>.json` in the project's folder), next to each reviewer's output (`review<n>-<name>.txt`); a card without one is graphed from its branch or merge commit. Why: attempts can be compared and reviewer findings laid on symbols with no new store. (change graph)
- 2026-11-11: Reviewers read the graph summary only when `graph.review_summary` is on (default off), and it is computed from the diff alone. Why: the reviewers' input stays as it was unless the user opts in, and the builder's words never reach them. (change graph)
- 2026-11-11: The secret guardrail says where (`possible secret in added line: path:line`), never what, and follows hunk headers so an added line starting with `++` is scanned too. Why: the old message did not say where to look; detection is the same or stricter. Approved by the user. (change graph)
- 2026-11-11: A name resolves to a symbol by name alone only when exactly one symbol has it and it is not a common one (`get`, `run`, ...); symbol ids are the first 12 hex digits of sha1(path, qualified name, kind). Why: a wrong edge misleads a reviewer more than a missing one, and stable ids make attempts comparable and links durable. (change graph)
- 2026-11-11: The web page asks for one symbol's diff lines when it is opened (never the whole diff) and draws up to 600 symbols, the list above that. Why: small responses and a canvas that stays responsive on big cards. (change graph)
- 2026-11-11: `run` no longer requires a clean tree. With the user's changes present it runs every card in a worktree (as `parallel` does) instead of the user's checkout. Why: the user asked to run with or without commits; in place, `git add -A` would sweep their work into a card. Asked by the user. (uncommitted changes; its first version also committed the orchestrator's own files by path, dropped by the next decision)
- 2026-11-11: Worktree cards land by `commit-tree` (the card branch's tree, parents base and card) plus `merge --ff-only`, after checking the branch contains base. Why: `git merge` refuses whenever anything is staged ("index must match HEAD"), while a fast-forward keeps unrelated staged, edited and untracked files and refuses, touching nothing, on an overlap. Checked by hand with git before relying on it. (uncommitted changes)
- 2026-11-11: The web Git tab follows the existing git policy: hooks only with `git_hooks`, literal top-level pathspecs, pull is fast-forward only, network calls get `GIT_TERMINAL_PROMPT=0` and a 3-minute limit, and no write while a `card/` branch or a detached HEAD is checked out. No discard button. Why: the same trust model as the orchestrator's own commits; nothing that can lose the user's work or hang the page. (git tab)
- 2026-11-11: Every file the orchestrator keeps for a project lives in `~/.lonerchestrator/projects/<name>-<sha1 of the path, 8>/` (`orch/folder.py`), not in the project or the temp folder; Claude Code is driven by flags (`--agents`, `--settings`, `--append-system-prompt`, `--add-dir` for the cards, context and memory only) instead of `CLAUDE.md`/`.claude/`; older projects are moved on the first command, copy first, delete last, only recognisable files. Why: the user asked that losing the project never loses the cards, context and memory; the OS empties temp folders; files in the project needed commits and `.gitignore` lines. Asked by the user. (project folder)
- 2026-11-11: A project that moved finds its folder by its first commit(s) (`git rev-list --max-parents=0 HEAD`, kept in the folder's `project.json`), not by its remote's address, and takes a folder only when exactly one matches and that folder's project is gone from its old path or replaced there by another repository. Why: the first commit is the same in every clone, needs no network and survives a renamed or missing remote; two clones side by side must not share cards, state and worktrees. Asked by the user. (project folder)
